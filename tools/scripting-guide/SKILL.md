# 写脚本的规范

## 何时用脚本

满足任一条就写脚本，而不是逐步推理或手工逐个改：批量或重复的机械操作；多步骤、手工容易出错的操作；需要精确结果的计算、统计、数据转换；结果需要可复现或可验证。

改一两处、一次性的简单问答，不写脚本。

## 临时脚本

- 放临时目录（client 提供的 scratchpad，或系统临时目录），不放进项目。
- 先查工具库（skill 列表或 `$AGENT_HOME/tools/INDEX.md`）里有没有现成的，有就按它的 SKILL.md 调用，不要重写。

## 写法

- **语言**：优先用项目已有的语言和运行时；没有约束时，简单的文件和文本处理用 shell，涉及数据结构的用 Python（只用标准库，除非确实需要第三方库）。
- **输入输出**：路径和参数从命令行传入，不写死。结果写到 stdout 或指定文件；日志和错误写到 stderr。
- **失败要明显**：出错时返回非 0 退出码，并给出能看懂的错误信息。shell 脚本开头用 `set -euo pipefail`。
- **会修改文件的脚本**：提供 `--dry-run`，先预览影响范围，确认后再真正执行。大批量修改前确认可以回滚（例如在 git 中且工作区干净）。
- **可验证**：执行后给出可以核对的摘要（处理了多少条、跳过多少条、为什么跳过）。
- **安全**：不在脚本里写入密钥；不执行来源不明的下载内容；删除操作只针对明确的路径。

## 执行之后

- 把脚本的关键结果汇报出来，说明怎么验证的。
- 如果这类任务可能再次出现，在收尾时它会被记入 `tools/candidates.md`。

## 沉淀成工具（确认后）

1. 起一个 id（小写 kebab-case，以后不改），建 `$AGENT_HOME/tools/<id>/`。
2. 写 SKILL.md：frontmatter 里 `name` 等于 id，`description` 一两句话说明做什么、什么时候用，`metadata.version` 从 "1" 开始。正文写用法、参数、注意事项，保持简短。
3. 入口脚本放 `scripts/main.*`，参数化，满足上面的写法要求。
4. 从 `tools/candidates.md` 删除对应候选，重新生成 `tools/INDEX.md`。
5. 只在一个项目里用的，放该项目的 `scripts/`，不进工具库。
