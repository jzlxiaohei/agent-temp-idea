# 01 问题拆解

## 起点

主流 harness client（Cursor、Claude Code、Codex 等）都用平铺的 session 列表。在 monorepo 场景下，希望能按“随便问问 / 前端 / 后端 / 优化 / 架构设计”等分组，组之间还有关系，形成图谱。担心：平铺太单薄，但分组 + 图谱又容易过度复杂。

## “列表不够用”背后的三个不同问题

| 痛点 | 场景 | 真正需要的 |
|---|---|---|
| 找不到 | “上周讨论缓存方案的 session 在哪” | 搜索、自动标签、维度筛选 |
| 上下文不连续 | 新开后端 session 要重新交代约定和历史决策 | **组级别的共享记忆** |
| 状态不清楚 | 同时开着多个 session，不知道哪个做完了 | 任务状态（看板） |

判断：**第二个价值最大**，也是平铺列表最做不到的。

## 分组 + 图谱为什么容易做过头

1. session 高频、低价值、多数一次性，人工分类的成本大于收益（类比书签文件夹、Evernote 笔记本）。
2. 横切问题：一个性能优化同时涉及前后端，树状分组放不下，至少要用多对多标签。
3. 全局图谱视图偏展示（参考 Obsidian / Roam 的 graph view），关系适合局部、按需出现。
4. 手工维护的关系会很快过时，关系应当自动推导（同一次 fork、改了同一批文件、同一个 PR/分支、显式引用）。

## 核心转向

- 分组的价值不在“归类”，而在“组本身带着上下文”：组记忆 + 新 session 自动继承 + 结束时写回。
- 更根本的一点：值得沉淀的是产出（代码、决策、知识），不是 session 本身。知识沉淀进文件后，session 列表退化成工作日志，平铺也无所谓。
- monorepo 的目录结构本身就是一套现成的分组。

## 建议的自检实验

翻最近 50 个 session，统计：

- 事后真正回看过几个？低 → 分类、图谱的投入回报不高
- 开头重复交代背景的有几个？高 → 组记忆值得做
- 同时属于两个以上组的有几个？→ 决定用标签还是文件夹
