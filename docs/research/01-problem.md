# 01 问题拆解

## 起点

主流 client（Cursor、Claude Code、Codex 等）都用平铺的 session 列表。希望按主题分组（例如一个项目下分“随便问问 / 前端 / 后端 / 优化 / 架构设计”），组之间还有关系，形成图谱。担心：平铺太单薄，但分组加图谱又容易过度复杂。

> 注：monorepo 只是一个例子。项目不一定有清晰的目录分层，也不一定是编码项目（写作、调研等）。下面的结论不依赖目录结构。

## “列表不够用”背后的三个不同问题

| 痛点 | 场景 | 真正需要的 |
|---|---|---|
| 找不到 | “上周讨论缓存方案的 session 在哪” | 搜索、标签、维度筛选 |
| 上下文不连续 | 新开 session 要重新交代约定和历史决策 | **组级别的共享记忆** |
| 状态不清楚 | 同时开着多个 session，不知道哪个做完了 | 任务状态（看板） |

判断：**第二个价值最大**，也是平铺列表最做不到的。

## 分组加图谱为什么容易做过头

1. session 高频、低价值、多数一次性，人工分类的成本大于收益（类比书签文件夹、Evernote 笔记本）。
2. 横切问题：一件事常常同时属于几个组，树状分组放不下，至少要多对多。
3. 全局图谱视图偏展示（参考 Obsidian / Roam 的 graph view），关系适合局部、按需出现。
4. 手工维护的关系很快会过时。

## 核心转向

- **组的价值不在“归类”，而在“组本身带着上下文”**：组记忆 + 新 session 读取 + 结束时写回。
- 不能假设目录结构就是分组，所以**“组”要显式定义**：一个主题文件就是一个组。
- 值得沉淀的是产出（决策、约定、踩过的坑、代码），不是 session 本身。知识沉淀进文件后，session 列表退化成工作日志，平铺也无所谓。
- 组之间的关系写在主题文件里，由 LLM 提议、人确认；不做全局图谱。

## 自检实验

翻最近 50 个 session，统计：

- 事后真正回看过几个？低 → 分类、图谱的投入回报不高
- 开头重复交代背景的有几个？高 → 组记忆值得做
- 同时属于两个以上组的有几个？→ 印证需要多对多
