# 03 意义评估

目的：动手之前严格判断值不值得做，避免做到一半才发现意义不大。

## 结论

**作为个人方法论值得做，成本很低；作为工程项目（尤其是记忆基建）大概率不值得做。**

## 反对的理由

1. **厂商迭代快**：格式层、存储层都在快速标准化和商品化，做在这两层容易白做。
2. **模型越强，手写上下文的边际价值越低**：模型自己读代码、检索的能力在提升；冗长的上下文文件可能有害（⚠️ 待核实）。
3. **收益难衡量**：自用只有一个样本，容易凭感觉高估。
4. **范围在膨胀**：讨论从 session 组织一路扩到组记忆、工具包、非编码项目、云端基建、prompt 原则。这是需要警惕的信号。
5. **最小版本已经能拿到大部分价值**：一个仓库、一个入口文件、一份原则 prompt、一份收尾 prompt，半天可以搭好。

## 支持的理由

1. 确实同时在用三家 client，而**跨厂商这件事没有哪个厂商有动力解决**。
2. 纯文本、归自己所有的知识，是**不随厂商变化而贬值**的资产。
3. 原则层和“脚本优先、复用再沉淀”这类**方法论**不会被功能更新取代，而且可以复利积累。

## 分项判断

| 部分 | 意义 | 决定 |
|---|---|---|
| 原则 prompt + 收尾写回流程 | 高 | 做，成本最低 |
| 纯文本记忆约定（个人 / 项目 / 主题三层） | 中高 | 做，保持极简 |
| 同步脚本、lint | 中 | 等真正感到痛了再写 |
| 第三方记忆服务 | 视需求而定 | 基线不够用时再选型接入，不自建 |
| session 组织界面和图谱 | 低 | 不做，交给厂商 |

## 停止条件

见 [experiment.md](../design/experiment.md)。两周实验后若满足任一条，就停在方法论层面，不再往工具方向投入：

- 收尾流程没坚持下来（说明问题不在工具）
- 没有感到明显收益

## 修订（2026-11）

上面的结论假设只需要共享记忆，并且靠文件约定就够。后续讨论修正了两点：

1. **约束要可靠**：只靠 prompt 和文件约定，读不读记忆、收不收尾、统计准不准，都取决于 agent 自觉。需要 hooks 在关键时间点强制执行。
2. **要能统一查看 session**：这是最初的需求，文件约定做不到，需要界面。

因此“session 组织界面”从“不做”改为“需要，但优先用现成工具”；方向是伴随 app，策略是组装现成工具、只补缺口。各部分已有大量开源项目，评估计划见 [04-existing-tools.md](04-existing-tools.md)。不自己做 client 的结论不变。
